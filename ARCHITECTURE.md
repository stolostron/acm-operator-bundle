# Architecture: acm-operator-bundle

## Overview

`acm-operator-bundle` is the **OLM (Operator Lifecycle Manager) bundle image
source** for Red Hat Advanced Cluster Management for Kubernetes (RHACM/ACM).
It packages the metadata OLM needs to install the ACM operator: the
ClusterServiceVersion (CSV), the `MultiClusterHub` CRD, a supporting webhook
`Service`, and bundle annotations/labels. The OLM package name is
`advanced-cluster-management`.

The operator this bundle installs is `multiclusterhub-operator`
(`registry.redhat.io/rhacm2/multiclusterhub-rhel9`). Once installed, creating
a `MultiClusterHub` custom resource triggers deployment of the full ACM hub
stack — roughly 45 component images spanning governance, observability,
search, application lifecycle, submariner, siteconfig, and more.

### Role in the ACM ecosystem

```
multiclusterhub-operator (built as an image + CSV/CRD source)
                │  (Konflux Snapshot captures component image digests)
                ▼
acm-operator-bundle           (this repo: assembles the OLM bundle)
                │  (bundle push pipeline "nudges" the catalog repo)
                ▼
acm-mce-operator-catalogs     (builds the File-Based Catalog)
                │
                ▼
OLM / OperatorHub on OpenShift
```

## Repository Structure

Like other bundle repos in this ecosystem, content differs substantially
between the `main` branch and release branches.

### `release-2.X` branches (generated bundle content)

| Path | Purpose |
|------|---------|
| `Dockerfile` | Builds the bundle image `FROM scratch`, copying `manifests/`, `metadata/`, `extras/`. |
| `manifests/` | The OLM bundle manifests: CSV, CRD, webhook `Service`. |
| `metadata/annotations.yaml` | OLM bundle annotations (mediatype, package, channel). |
| `extras/<version>.json` | Resolved image manifest — every image with digest + git provenance. |
| `config/` | Generation inputs/templates (CSV template, manifest-gen config, bundle-gen config, Dockerfile template). |
| `latest-snapshot.yaml` | Konflux `Snapshot` CR — the trigger/input for bundle regeneration. |
| `BUILD-NUMBER`, `Z_RELEASE_VERSION` | Build iteration number and base release version. |
| `.tekton/` | Konflux/Tekton PipelineRun definitions (push + pull-request). |
| `.github/workflows/` | GitHub Action that regenerates bundle contents when triggered. |

### `main` branch (tooling only — no generated manifests)

Holds a `Makefile`, `scripts/`, and shared workflow/config plumbing used for
**image verification and CVE scanning**, not for bundle building.

## Core Components

### Bundle labels & annotations

`Dockerfile` (`FROM scratch`) sets both OLM operator-framework labels
(`mediatype.v1`, `manifests.v1`, `metadata.v1`, `package.v1=advanced-cluster-management`,
`channels.v1=release-2.13`) and Red Hat delivery/Konflux labels
(component name, version/release, CPE, `konflux.additional-tags`).
`metadata/annotations.yaml` duplicates the OLM annotations.

### ClusterServiceVersion (`manifests/advanced-cluster-management.v<version>.clusterserviceversion.yaml`)

- Declares `spec.version`, `spec.replaces`, and `olm.skipRange` for the upgrade graph.
- `operatorframework.io/initialization-resource` and `alm-examples` both point at a `MultiClusterHub` sample.
- `installModes`: OwnNamespace only.
- `spec.install.strategy: deployment` — a single `multiclusterhub-operator` Deployment (2 replicas, pod anti-affinity, leader election) with ~48 `OPERAND_IMAGE_*` environment variables, each pinned to a `registry.redhat.io/...@sha256:` digest. This is how the operator learns which component images to deploy.
- `spec.relatedImages` mirrors the `OPERAND_IMAGE_*` values for OLM/mirroring support in disconnected environments.

### CRD (`manifests/operator.open-cluster-management.io_multiclusterhubs.yaml`)

`MultiClusterHub` — namespaced, shortname `mch`, generated by controller-gen.

### Webhook `Service`

Routes traffic on port 443 → 9443 to pods labeled `name: multiclusterhub-operator`, with an OpenShift service-serving-cert annotation.

### Generation inputs (`config/`)

- `acm-csv-template.yaml` — the CSV skeleton with placeholder markers filled in during generation.
- `acm-manifest-gen-config.json` — maps each product image to its Konflux component and published name, plus a list of pinned external images.
- `acm-bundle-gen-config` — bash configuration consumed by the shared generation tooling (OCP version range, supported archs/OS, EUS configuration, package name).
- `Dockerfile.in` — templated Dockerfile.

## Data / Control Flow

1. Konflux builds each ACM component image and produces/updates a **Konflux `Snapshot`** listing every component image digest and its source git revision.
2. A bot commits the updated `latest-snapshot.yaml` to the release branch via PR.
3. `.github/workflows/gen-bundle-contents-when-triggered.yaml` fires on that PR (`pull_request_target`), authenticates to registries, and runs `tools/run-script-from-tools-repo config/bundle-pr-config-vars`.
4. That shim clones `stolostron/release` and invokes the shared bundle-generation logic, which consumes the Snapshot plus `config/*` to regenerate `manifests/*.csv.yaml`, `extras/<version>.json`, and `Dockerfile`, and bumps `BUILD-NUMBER`.
5. The regenerated files are committed back to the release branch.
6. The Konflux `.tekton` pipeline builds the bundle image and pushes it; the push pipeline's `build-nudge-files` annotation triggers regeneration of the downstream FBC catalog in `acm-mce-operator-catalogs`.
7. OLM ultimately reads the catalog → the bundle image → the CSV/CRD to install/upgrade the operator in-cluster.

## Build, Test & Release

- **Dockerfile**: `FROM scratch`; pure metadata image, no executables.
- **Konflux/Tekton** (`.tekton/`): push and pull-request PipelineRuns referencing the shared pipeline `pipelines/common-oci-ta.yaml` in `stolostron/konflux-build-catalog`; hermetic builds; push pipeline nudges the catalog repo.
- **GitHub Actions**: `gen-bundle-contents-when-triggered.yaml` for content regeneration.
- **`main`-branch Makefile** (verification/CVE tooling only): `list-images`, `verify-images` (+ per-arch variants), `scan-cves`, `image-report`, `setup-release`.
- **Version/branch mapping**: `Z_RELEASE_VERSION` + `BUILD-NUMBER` compose the image `version`/`release` (e.g. `2.13.7-328`); OLM channel is `release-2.13`.

## Dependencies & Integrations

- **`stolostron/multiclusterhub-operator`** — the operator whose CSV/CRD this bundle ships.
- **`stolostron/acm-mce-operator-catalogs`** — downstream FBC catalog, nudged by the bundle push pipeline.
- **`stolostron/release`** — shared bundle-generation tooling.
- **`stolostron/konflux-build-catalog`** — shared Tekton pipeline definitions.
- **~46 ACM product components** (each a separate `stolostron/*` repo) and a handful of pinned external images (configmap-reloader, postgresql, memcached, redis, etc.), all referenced by digest.
- **Konflux/AppStudio** (`crt-redhat-acm-tenant` tenant) as the build system.

## Conventions & Patterns

- **`main`** holds shared tooling/config/scripts only; **`release-2.X`** branches hold generated bundle content; short-lived RC/build-staging branches exist for point releases.
- **Versioning**: `X.Y.Z-BUILD` derived from `Z_RELEASE_VERSION` + `BUILD-NUMBER`; CSV name is `advanced-cluster-management.vX.Y.Z`; channel is `release-X.Y`.
- **Upgrade strategy**: `replaces` (immediate predecessor) plus `olm.skipRange` for multi-version skip upgrades.
- **Everything is generated** — manual edits belong in `config/` on the appropriate branch, not in the generated `manifests/`/`Dockerfile`.
- **All shipped images pinned by `@sha256` digest** for reproducibility and disconnected/FIPS support.
- **Multi-arch**: amd64, ppc64le, s390x, arm64.
